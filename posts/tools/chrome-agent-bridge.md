# 市面上的 AI 浏览器很多，为什么我还是把日常 Chrome 借给它

现在衡量一个人到底能不能把 AI 用出深度，很多时候看的就是那个浏览器。

把提示词写得再花哨，如果 AI 只能呆在对话框里回文本，天花板肉眼可见。日常运维排查云平台故障、看监控看板的告警日志、去各家系统核对账目，或者做深层背景调查、跨平台收集未公开的资料，绝大多数真正有价值的信息根本没有标准 API。想要拿到这些内容，唯一入口就是浏览器。

AI 伸手够不到浏览器，就只能在门外看热闹；能操控浏览器，它才算真正下场替你干活。

市面上解决这个问题的方案不少，但我自己折腾了一圈，发现现成的工具几乎每一个都卡在某种让人难以忍受的别扭里。

## 定制浏览器很酷，但真人日常根本不用

第一种路线，是这两年冒出来的各种定制浏览器。很多团队针对 AI 场景专门魔改或者打包了独立的浏览器环境，号称自带 Agent 沙箱，能力拉满。

这类工具看起来很美，却踩中了一个最朴素的常识。那是给机器跑代码用的，真人日常根本不会把它当主力。

现实里，我们所有的工作和生活状态全留在主力 Chrome 上。公司内部的 SSO 单点登录、阿里云或 AWS 的控制台、GitHub、邮箱、日常沟通工具，还有各种零碎的内容平台，几十个账号的登录态和 Cookie 全在里面。

如果让 AI 去操控一个全新的定制浏览器，每次想让它帮着查点东西，你得先把这一长串账号密码重新登录一遍。碰到扫码验证或者两步验证，更是折腾得焦头烂额。原本是为了省两分钟时间让 AI 跑个巡检，结果光搬运登录态就耗掉半小时。

日常干活，没人愿意专门给 AI 伺候一个空壳浏览器。

## 弹窗烦到崩溃，或者被风控一枪打死

定制浏览器走不通，很自然就会想到第二条路：直接连本地的 Chrome。

这也是很多开源项目和 Skill 采用的路线，但跑起来依然处处碰壁。

最典型的做法是直接挂 Chrome DevTools Protocol，也就是 CDP 远程调试。像不少人常用的 web access 这一类插件，底层走的都是这条道。只要调起浏览器，Chrome 就会疯狂弹窗。窗口顶部死死贴着一条刺眼的黄色警告“Chrome 正在受到自动测试软件的控制”，时不时还会弹出一个权限确认弹窗。你手头正敲着代码或者查着资料，屏幕上冷不丁弹出一个窗口打断输入，一次两次还能忍，一天弹几十次真的让人心烦意乱。

另一类做法更粗暴，直接拿 Playwright 或者 Puppeteer 来驱动。Playwright 本来是给测试人员写端到端自动化测试用的，设计初衷是让它在流水线上跑代码断言，不是给日常 AI 当手脚。自动化测试框架身上带着极浓厚的机器特征，`navigator.webdriver` 标记永远常开，底层的指纹也和真人环境截然不同。

稍微有一点风控意识的网站，不管是小红书、各类业务管理后台，还是高防的内容社区，一撞上去就是无休无止的滑块拼图和验证码，严重的甚至直接 403 封禁。AI 连正文都还没扫到一眼，第一步就直接被堵在门外。

## 把天天在用的 Chrome 借出去

弹窗太烦，测试框架又跑不通高风控，剩下的路就很清楚了。

既然所有的登录态、最干净的真实指纹都在我们日常使用的 Chrome 里，那就把手头的 Chrome 借给 AI。

这也是 OpenAI 的 ChatGPT for Chrome 和 Anthropic 的 Claude in Chrome 官方插件给出的参考。不在外面挂着调试器敲门，而是写一个原生扩展装进 Chrome 内部，通过操作系统的 Native Messaging 管道跟本地进程通信。

我写的这个小工具叫 chrome-agent-bridge，核心逻辑就按这个架构来跑。

电脑本地跑一个极轻的转发服务，Chrome 里装一个专用的 MV3 扩展。AI 客户端通过本地端口把指令发给服务，服务通过系统级原生消息管道塞给扩展，扩展在浏览器内部去读 DOM、点按钮、滚屏幕、截长图。

这套结构避开了上面的全部坑点。

首先，它直接跑在你的主力 Chrome 里，所有日常账号免密直通，不需要迁移任何 Cookie。

其次，它不走外部 CDP 调试端口，Chrome 顶部绝对不会弹出那条烦人的自动测试黄色警告，全程安安静静，不抢焦点不弹窗打扰。

再次，它借用的是你的真实浏览器环境和真实 TLS 指纹。在风控系统眼里，这就是你在正常点开一个网页，不会动不动触发滑块死循环。

## 看得见、拦得住、不打架

把主力浏览器交出去，最让人担心的永远是失控。

万一 AI 脑子一抽，在后台乱删数据或者乱点确认怎么办？万一页面上有银行卡号或者密码，全被它读走怎么办？多开几个 Agent 任务，它们会不会争抢同一个标签页？

这些问题不解决，工具写出来也没人敢放心用。在 chrome-agent-bridge 里，我把交互边界卡得很死。

第一，AI 动了哪里，眼睛看得清清楚楚。AI 一旦接管某个标签页，标题栏立刻带上醒目的红点标记“● Agent 接管中”，扩展图标上也会亮起蓝色徽标。在页面内部，AI 每次点击都会浮出一个半透明的“幽灵光标”并带有一圈扩散涟漪，它点了哪个按钮、准备点哪里，轨迹一目了然。

第二，右上角随时能一脚踢开。页面右上角常驻一个红色的“停止 Agent”按钮。看着它动作不对劲，鼠标甩过去点一下，控制权立刻被掐断。AI 如果在操作中途停下来思考，超过 12 秒没有发来下一条指令，接管状态会自动解除，标签页原标题随之恢复。

第三，多个 Agent 协同不抢地盘。工具允许两三个本地 Agent 同时连进来。不同的标签页完全支持并行，比如一个 Agent 在标签页 A 排查云服务器日志，另一个 Agent 在标签页 B 检索技术文档，互不干扰。针对同一个标签页，内置了严格的排队锁和状态感知，前面的动作没执行完，后面的指令老老实实排队等待。如果哪个 Agent 意外崩溃忘了释放，120 秒超时机制会自动兜底解锁，绝不把标签页卡死。

第四，敏感数据绝不过 AI 的手。在读取页面内容这一步，代码里内置了脱敏拦截。遇到密码输入框，或者 `autocomplete` 属性带有信用卡号、卡片三位安全码、短信动态验证码的字段，内容会被统一打码成 `[value redacted]` 后再传给 AI。AI 能帮你看页面，但碰不到你的真实密码和卡号。

## 它能做什么，做不了什么

这套工具目前在我自己的机器上承担了挺多琐碎任务。

比如日常运维，让 AI 登录云厂商控制台，点开不同实例的监控图表，把异常抖动和报警日志抓下来汇总。

比如深入调研，查某些特定话题时，让 AI 深入那些需要登录的社区，把折叠的几十层二级回复全部展开，剔除营销软广，整理成干净的数据结构。

比如后台批量打理，处理特定业务后台里的重复表单与状态流转。

讲完它能做的，也要把做不到的边界讲透。

它目前只适配了 macOS 配合 Google Chrome 的环境，其他系统和浏览器还没做支持。

它绝对不替你登录。遇到必须手动扫码、输入密码、接听语音验证码的节点，AI 会停下所有动作，在终端里提醒你接手。只有当你手动搞定认证、页面跳回正常状态之后，它才会接着往下跑。安全红线绝不越位。

它不是给完全不懂技术的人准备的双击安装包。它的交互核心是一套命令行和本地 RPC 接口：

```bash
node agent/cli.mjs tabs
node agent/cli.mjs open https://example.com
node agent/cli.mjs click "button[type=submit]"
```

它是造给本地那些 AI Agent、脚本或者自动化工作流当手脚用的。如果你日常已经习惯用各类 AI 助手帮着处理任务，把它接上去，AI 就能多出一双能碰触真实网络的手。

项目开源在 GitHub：[zqcccc/chrome-agent-bridge](https://github.com/zqcccc/chrome-agent-bridge)。

把 AI 关在聊天框里，很多活永远落不到地上。真要下场干活，不用大费周章重新造个新机器，把手头天天在用的家伙安全借给它，就能省下大半力气。
